# 运行期内存实测（探针埋点）

- 日期：2026-11-01
- 被测固件：`llm-client` @ `7b8e306` + 探针埋点 memprobe（本次提交）
- 硬件：ESP32-D0WD-V3（240 MHz，4 MB Flash），串口 115200
- 测量手段：`memprobe`（`memprobe.h/.cpp`）在请求各阶段打点，串口输出 `[mem]` 行；
  采集脚本 `memrun.py` / `tls_rep.py`（HTTP 触发 + 串口并行读取）

---

## 一、先立口径：两个"堆"

| 口径 | 数值 | 来源 | 含义 |
|---|---|---|---|
| 链接期 DRAM 堆段 | **161,784 B** | `0x40000000 − 0x3FFD8808`（`.bss` 之后到 DRAM 末尾） | 内存分布图用的就是这个数 |
| 运行期 `ESP.getHeapSize()` | **262,236 B** | 串口 `[mem] begin` 行 | = DRAM 222,152 + IRAM 40,084（`heap_caps` 口径） |

`getFreeHeap()` 是相对 **262,236** 算的，不是相对 161,784。两者差 100,452 B，来源：

- **IRAM 空闲段 40,084 B**：`0x4009636C` 起，链接期算"IRAM 空闲"，运行期被收进内部分配器；
- **WiFi/BT 保留窗 60,368 B**：`0x3FFAE000–0x3FFBDB5C` 这段在链接期是"ROM 数据 + BT 保留"，
  运行期由 `heap_caps` 管起来；实测其中 7 个区段共 62,536 B，**分配已占 56,912 B、几乎无空闲**
  （WiFi 栈初始化时就吃掉了）——所以它"算在堆里"，但**不是可用余量**。

> 结论：**图上的"堆 161,784 B"作为"静态区之后的 DRAM 段"没错，但拿它当"总堆"去算空闲率、
> 算"已用 7,020 B"是错的**。真实基线见下节。

## 二、启动 / 空闲基线（复位后首轮请求开始前）

```
[mem] ===== begin: upload | heapsize=262236 free=155408 blk=110580 | chip=ESP32-D0WD-V3 rev301 240MHz
```

| 项 | 数值 |
|---|---|
| 空闲堆 | **155,408–155,428 B**（两次复测各一次） |
| 最大连续块 | **110,580 B** |
| 栈余量（since-boot 水位） | 5,324 B（8192 中已用 2,868） |

`getHeapSize − getFreeHeap = 106,808 B` 的去向（`heap_caps_print_heap_info` 原始输出）：

| 去向 | 约数 |
|---|---|
| WiFi/BT 保留窗内已分配（7 段） | 56,912 B |
| `.bss` 之后 DRAM 堆区已分配（含 loopTask 8 KB 栈、WebServer、LittleFS 等） | 28,636 B + 10,092 B |
| IRAM 内已分配 | 20 B |
| 分配器块头/元数据（不计入 allocated 统计） | ≈11 KB |

这同时**解掉了 2026-10-31 记下的疑点**：「`getFreeHeap` 应比堆总量少 8,192，实测只少 7,020」
—— 那个 7,020 是拿 161,784 当总量算出来的（161,784 − 154,764），基数本来就错，
不是栈的账对不上。

## 三、一次 Ollama 请求的分阶段占用（代表性一轮，"hi"）

| 阶段 | 距本轮起点净增 | 本轮累计峰值 | 最大连续块 |
|---|---|---|---|
| uploaded（明文已落静态工作区） | 0 | 0 | 110,580 |
| parsed（就地零拷贝解析） | 0 | 0 | 110,580 |
| chunk_begin | +728 | 728 | 110,580 |
| pre_connect | +948 | 948 | 110,580 |
| tcp_up | 0 | 948 | 110,580 |
| head_sent | +1,576 | 1,576 | 110,580 |
| req_sent | +2,908 | 2,908 | 110,580 |
| resp_head | +1,048 | 2,908 | 106,484 |
| first_delta | +1,876 | 2,908 | 106,484 |
| stream_end | +1,184 | 2,908 | 106,484 |
| upstream_closed | 0 | 2,908 | 110,580 |
| llm_done | 0 | 2,908 | 110,580 |
| **done_written** | **+9,284** | **9,284** | 102,388 |
| **resp_end** | **+10,940** | **10,940** | 98,292 |
| released（工作区只标记、不释放） | 0 | 10,940 | 110,580 |
| end | 0 | 10,940 | 110,580 |

要点：

1. **上传与解析两段堆占用为 0** —— 明文 payload 直接落 `g_work`（48 KB 静态区），
   `deserializeJson` 就地解析，没有中间 String。
2. 上游请求期间只花 **2–3 KB**（TLS 之外）。
3. 峰值出现在**收尾**（`done_written` / `resp_end`）的 6–15 KB，不是上游交互期；
   这部分是 chunk 回写与逐行 `serializeJson` 的瞬时分配，随每轮释放。

## 四、四类场景的实测峰值

| 场景 | 峰值占用 | 峰值时的最大连续块 | 备注 |
|---|---|---|---|
| A. Ollama「hi」连发 3 轮 | 10,940 / 8,432 / 11,264 B | ≥98,292 B | 每轮结束回到 ~156 KB 空闲，无累积 |
| B. Ollama 长回答（10.1 s） | 9,296 B | 102,388 B | 流式时长变长不显著抬高堆 |
| C. 前端同款 gzip 上传 + 2 KB 历史 | 14,880 B | 94,196 B | 压缩体收在 2,180 B 的 String 里，解压后即释放 |
| D. DeepSeek（TLS）单次 | **65,712–66,924 B** | **45,044–47,092 B** | 见下节，量级完全不同 |
| E. DeepSeek 连发 4 次 | 65,712 / 64,952 / 66,208 / 65,624 B | 每轮发送请求体瞬间最低 47,092 B | 峰值稳定，无增长 |

## 五、TLS 是唯一的大头（DeepSeek 场景）

```
[mem] pre_connect  free=149912 used=2560  blk=106484
[mem] tls_up       free=105864 used=46608 blk=61428   ← 握手一次性 +46.6 KB
[mem] req_sent     free=85548  used=66924 blk=45044   ← 本轮最坏
[mem] upstream_closed free=150236 used=2236 blk=61428
```

| 项 | 实测 |
|---|---|
| `tls_up` 跳变（握手开销） | **46,124–46,644 B**（旧报告估 32,000–40,000，偏小） |
| 峰值占用 | **65,712–66,924 B**（占 `getHeapSize` 的 25%） |
| 峰值时最大连续块 | **45,044 B**（请求体发送瞬间）；稳态 61,428–63,476 B |
| 最低空闲 | 85,548–88,396 B |
| 栈最深处 | 余 4,000–4,012 B（8192 中用掉 ~4,180） |

**碎片不回弹**：跑过一次 TLS 之后，最大连续块从 110,580 掉到 **63,476 B** 并一直保持到下次复位
（TLS 缓冲区释放了，但堆不合并）。连发 4 次没有继续恶化，所以是"一次性碎片"而非泄漏。

对现有设计的含义：

- `WORK_BUF_SIZE` 是静态区，**不占堆、也不受碎片影响**，48 KB 请求体上限仍然确定；
- 但"最大连续块"这个数**不能再用 110 KB 报**：最坏是 TLS 发送期的 **~45 KB**，
  TLS 之后是 ~63 KB。异步/并发的任何新分配（未来若恢复动态工作区）都应按 ~45 KB 估。

## 六、结论

1. **不会撑爆**：各场景峰值都不超过 67 KB，最坏 25% 占用；空闲堆在收尾后回到 ~155 KB。
2. **真正的大头只有 TLS**：46.6 KB 握手 + 峰值 67 KB；其余（明文/gzip/历史/长回答）都在 3–15 KB。
3. **图上三处旧数需要按本节更新**（若图继续维护）：
   - "空闲 154,764 B" → 实测 155,408 B（差异来自复测时机，同量级）；
   - "最大连续块 40–65 KB" → 空闲时 110,580 B、TLS 后 63,476 B、最坏 45,044 B；
   - "已用 7,020 B" → 口径错误，真实 `getHeapSize − getFreeHeap = 106,808 B`（含 WiFi/BT 静态 57 KB）。
4. **仍不确定的**：IRAM 40,084 B 是否真能用于请求期的大块分配（`MALLOC_CAP_8BIT` 不含 IRAM8，
   应用侧从未显式申请 IRAM 堆），本次没有单独验证。

## 七、复现方法

```bash
# 准备机（能连板子 + 有串口）上
cd ~/esp32-work/llm-client && ./tools/build.sh          # 编译 + 烧录（含探针固件）
scp memrun.py user@<本机>:/tmp/                       # 采集脚本：Ollama×3 / 长回答 / gzip / DeepSeek
python3 /tmp/memrun.py                                   # 复位板子 → 串口并行采集 → 打印每阶段表
python3 /tmp/tls_rep.py                                  # 连发 4 次 DeepSeek，看碎片是否累积
```

串口原始日志：`/tmp/memrun-raw.log`；采集输出：`/tmp/memrun-out.txt`、`/tmp/tls_rep.txt`。
