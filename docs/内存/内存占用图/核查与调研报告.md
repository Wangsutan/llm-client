## 三、关于「64 KB」的核实

你提到「专门分了 64 KB」。核查结果：**源码中不存在 64 KB 版本**。

| 检查点 | 值 |
|---|---|
| `llm_limits.h` | `#define WORK_BUF_SIZE (48 * 1024)` |
| 编译产物 `.map`（与源码同一分钟，01:14） | `g_work` = `0xc001` = 49,153 B |
| git HEAD | `df34781`，工作区干净 |
| `.30` / `.20` / `.22` | 无此项目 |

64 KB 出自 `内存瘦身审查.md` 的「已知取舍」段：*"想抬上限只需改 `WORK_BUF_SIZE` 一个常量（例如 64KB → 约 21,000 字）"* —— 那是一条**建议**，代码未落实。因此本图按 **48 KB** 绘制，与板子上实际烧录的固件一致。

## 四、版式核查（脚本化）

写了 `check_layout.py`，解析 SVG 后检查四类问题：画布越界、柱内文本越界、竖向压字、零尺寸矩形。

### 4.1 已修正的 3 处真问题

1. **Flash 开头 5 个小分区**：4 MB 等比缩到 894 px 后，bootloader（24,992 B）只有 5 px、分区表（224 B）只有 0.05 px，塞 7.5 px 数字必然压叠。
   **改法**：图上保留纯色真比例块，整体加虚线框引出，右侧做**放大表**（教材处理微小区段的通行做法）。
2. **`.bss` 标题压 `g_cnxMgr`**：`.bss` 标签与第一个库符号只差 5 px。
   **改法**：库块（`g_cnxMgr` / `s_wifi_nvs` / `dns_table`）标签全部移到柱右侧，用引线指回——块本身仅 1–3 px 高，放不下字。
3. **三张小卡片与地址轴重叠**：初版 `CY=760` 落在轴内（轴到 1000）。
   **改法**：卡片下移到 `CY=1046`，画布加高到 1380。

### 4.2 剩余脚本告警 = 误报

- 坐标轴刻度（`0x3FFAE000` 等）：`text-anchor="end"` 本身就向右回退，脚本按"落在柱内"误判。
- 页脚说明、卡片文字：整页宽文本，本就跨柱。
- 图例色块：y 方向按 21 px 排布，字号 8.5，脚本阈值 0.8×字号 误判。

## 五、已知局限（必须说明）

1. **我没有目视验证 PNG。** 当前模型不支持读图，图是否"好看"、字是否有挤压、CJK 是否缺字，我只能靠坐标计算推断，**不能保证观感**。
2. **字体走 fallback。** SVG 声明 `Source Han Sans SC → Noto Sans CJK SC`；渲染在 `.30` 上做（`rsvg-convert` + fontconfig），该机两者都有。
3. **堆内部色块是示意。** 已用块/空洞的**位置与大小**是示意性的（真实碎片分布随时变化），只有"空闲 154,764 B""最大连续块 40–65 KB"是实测值。图例已注"堆已用块"，未标注具体归属，避免误导。
4. **`g_inflater` 的 10,992 B 是 map 符号大小**，不等于运行时堆开销（它在 `.bss`，不占堆）。

## 九、终检：全量客观数据复核（2026-10-31 收尾轮）

对图上每一个数字重新溯源，不采信图上字面值。**发现并修正 3 处客观数据错误。**

### 9.1 修正明细

| # | 项 | 图上有误值 | 实测正确值 | 依据 |
|---|---|---|---|---|
| 1 | bootloader 大小 | 24,233 B | **24,992 B** | `llm-client.ino.bootloader.bin` 文件大小 = 24,992 B；`merged.bin` 在 `0x1000` 处最后非 0xFF 字节偏移 0x619F → 24,992 B |
| 2 | 分区表大小 | 210 B | **224 B** | `part.bin` 内容长 224 B = 6 条 × 32 B + 1 条 MD5（`0xEBEB`）32 B |
| 3 | 卡片②算式 | `320 KB − 64 KB − 110 KB = 161,784` | 见 9.2 | 该式实数结果 149,504 B，与 161,784 相差 12,280 B，等式不成立 |

### 9.2 卡片②的正确推导

```
DRAM 跨度  0x40000000 − 0x3FFAE000 = 335,872 B  (328 KB)
− ROM/BT  0x3FFBDB5C − 0x3FFAE000 =  64,348 B
− .data    0x3FFC3EA5 − 0x3FFBDB60 =  25,413 B
− .bss     0x3FFD8808 − 0x3FFC3EA8 =  84,320 B
− 段间对齐填充                        =       7 B
= 堆       0x40000000 − 0x3FFD8808 = 161,784 B  ✓
```

静态区 25,413 + 84,320 = **109,733 B**（原图写「110 KB」是四舍五入，作为被减数会带 627 B 误差，已改为精确值）。
四个 DRAM 段之和 335,865 B + 对齐 7 B = 335,872 B，与跨度自洽。

> 关键点：DRAM **不是** 320 KB。320 KB 是 `.bss` 起点往上到 `0x40000000` 的可用区间，`0x3FFAE000–0x3FFC0000` 这 72 KB 已被 ROM 数据与 BT 保留占用。原算式用 320 KB 作基数必然凑不上。

## 十、合并旧版内存分布图（2026-11-01）

`docs/内存分布图.dot`（2026-10-31 提交）报出了堆 217,944 B，与本次实测的 161,784 B 冲突。

### 10.1 旧图数字错在哪

| 项 | 旧图 | 实测 | 性质 |
|---|---|---|---|
| 堆总量 | 217,944 B | **161,784 B** | 按 `320 KB − 静态区` 算，漏扣 `0x3FFAE000–0x3FFBDB5C` 的 64,348 B ROM/BT 保留区 |
| "库基线 63,180 B" | 当作堆内已占 | **不存在** | 由 `217,944 − 154,764` 反推，非实测；所列 WiFi RX / lwIP / LittleFS 均在 `.bss`，已计入静态区，属重复计数 |

| 固件大小 | 1,137,548 B / 86% | **1,137,696 B / 86.8%** | 差 148 B |
