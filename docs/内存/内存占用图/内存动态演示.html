TLS 是大头。握手一次就多出 46,644 B（SSL 内容缓冲 16 KB×2 是 mbedtls 编译期常量，调小不了）。接 DeepSeek 时单请求峰值 65,712–66,924 B， 空闲堆从 155,408 B 掉到 85,548 B，最大连续块在发送请求体那一瞬掉到 45,044 B——这期间如果系统要临时分配大块，余量就没那么宽了。

数据来源与局限

实测：DRAM 四段起止来自 link map；空闲 155,408 B、最大连续块 110,580 / 63,476 / 45,044 B、各阶段增量均来自 memprobe 串口埋点 （2026-11-01，见 docs/内存/内存实测-探针-2026-11-01.md）。

各阶段数值：同一轮请求里按 [mem] 行逐点采样，不再是估算； 收尾阶段 6–15 KB 峰值的具体分配点还没定位（chunkWrite 本身不分配）。

为什么没有并发：web_server.cpp:14 用的是同步 WebServer， handleChat 从 chunkResponseBegin 一路阻塞到 llmStream 返回才结束；webHandle() 即 server.handleClient()，跑在主循环里。 同一时刻只能有一个请求在处理，不存在并发叠加的场景。

其他存储为何不动：一次请求只从堆取内存。 .data / .bss 是链接期定好的静态区，运行中不改； ROM 数据 + BT 保留区由硬件与协议栈固定； IRAM 存的是代码，请求跑起来不会变大； Flash 里的 app0 与 LittleFS 只在烧录或写文件时变，聊天不碰。

唯一会写 Flash 的动作是改配置：handleConfigPost → llmSetBackend → gPrefs.putInt("backend", ...)， 要擦写一个 nvs 扇区（几十毫秒，期间 flash cache 被禁用）。 代码在 llm_client.cpp:42-45 专门做了判断：值没变就不写。 上方的 nvs 色块闪烁就是对这一步的示意。

没建模：任务栈（loopTask 8 KB，实测空闲时用 2,868 B、TLS 深点用 4,192 B， 创建时 malloc、恒定）、IRAM（128 KB，运行期其空闲段并入内部分配器）。

旧的 7,020 B 疑点已解：那是拿 161,784（.bss 之后的 DRAM 段）当堆总量算的； getFreeHeap 相对的是 getHeapSize()=262,236 B（DRAM 222,152 ＋ IRAM 40,084）， 真实已分配 106,808 B，其中 WiFi/BT 保留窗 56.9 KB、.bss 之后 38.7 KB（含 8 KB 栈）。
