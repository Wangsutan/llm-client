## 硬件与运行时事实（实测）

- 芯片：ESP32-D0WD-V3，xtensa LX6 双核 240MHz，**520KB SRAM，无 PSRAM，无 SD 卡**；4MB Flash。
- Arduino-ESP32 core **3.3.12**（IDF 5.x），GCC 14.2。
- 固件占用 **1,135,888 / 1,310,720 字节（86%）**；分区表是 core 的 default：
  `app0 0x10000 (1280KB)`、`app1 0x150000`、`spiffs 0x290000 (1408KB，放网页)`、`coredump 0x3F0000 (64KB)`。
- **实测空闲堆 ~200KB**，但**最大连续可分配块只有 40–65KB**（这是最关键的约束：堆总量够、连续块不够）。
- 一轮 45KB 明文历史的对话，进入 chat 处理时 free heap ≈ 121KB。
- SDK 编译选项（从 `sdkconfig.h` 读到）：`CONFIG_HEAP_TRACING_OFF`、`CONFIG_HEAP_POISONING_LIGHT=1`、
  `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK=1`、`CONFIG_ARDUINO_LOOP_STACK_SIZE=8192`、
  `CONFIG_ESP_TASK_WDT_PANIC=1`（5 秒）、`CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH=1`（ELF 格式）。
- Arduino core 的 `WebServer` 被本地打了两个补丁（见 `project/tools/core-patch-webserver.md`）：
  `chunkWrite` 遇到部分 TCP 写会重试；`chunkResponseBegin` 会 `setSSE(true)`。补丁本身也可能有内存代价。

## 数据流（供你快速定位，但不要被它框住）

浏览器 → `POST /api/chat`（multipart，字段是带 `.gz` 文件名的 payload）→ 板子 `handleUpload()`
（分块累积 → `gzipParse()` 读 ISIZE → `payloadCap()` 判上限 → `gzipInflate()` 用 ROM tinfl 解压到
malloc 缓冲）→ `handleChat()`（`deserializeJson` 零拷贝解析那块缓冲）→ `llmStream()` 分发到
Ollama（裸 socket、chunked 请求体、逐条序列化消息）或 DeepSeek（WiFiClientSecure + Bearer）→
`streamLines()` 自解 chunked 并按行回调 → 合并 delta ≥64 字符后 `chunkWrite` NDJSON 回浏览器。
另有一条 `/api/summarize`（历史压缩）走同一条上传管线；`/api/config`、`/api/models` 是 JSON 小接口。

## 我们要你回答的问题

1. **哪些地方可能被撑爆？** 不是"理论上可能"，而是"从代码看，什么输入/时序/状态会触发"。
   每条给出：触发条件、涉及代码位置（`文件:行号` + 关键代码片段）、为什么会爆（堆总量？连续块？栈？）、
   爆的后果（重启 / 卡死 / 返回错误 / 静默失败）。
2. **哪些"防护"其实没防住？** 项目现在有这些自认为能兜住的东西，请逐个挑战它们：
   `payloadCap()`（= min(200KB, 最大连续块 − 24KB)）、gzip 上传、零拷贝解析、`releasePlain()`、
   `readPayload()` 的 413/400、`chunkWrite` 合并缓冲、`SUMMARY_INPUT_MAX` 截断、
   `WiFiClient`/`WebServer` 超时、`Preferences`（NVS）配置。
3. **有没有长期运行的隐患**（不是单次爆炸，而是跑几天后变差）：碎片、泄漏、计数器回绕、String 增长、
   连接未关闭、任务栈缓慢消耗、LittleFS 句柄、NVS 写入磨损。
4. **栈与并发角度**：`loopTask` 只有 8KB 栈；`loop()` 里同时跑 WebServer、串口控制台、LLM 流式转发。
   有没有递归、大对象上栈、重入（比如流式转发中来一个新请求）、回调里再分配内存之类的风险？
5. **可以怎么改**：每条风险给出可落地的改法 + 代价（Flash/RAM 增量、代码量、风险）。
   如果某个风险的改动代价远大于收益，直接说"不值得改"。
6. **最后给一个排序**：最危险的 3 条（或者说"如果只改 3 处，改哪儿"）。
