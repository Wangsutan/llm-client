## 一、风险清单（按它自评的危险度排序）

## #1 明文回退路径让整包请求体一次性进入堆（malloc/realloc）

**①现象**
前端 `payloadForm()` 在 `CompressionStream` 不可用或抛异常时，退化为明文 multipart（字段名 `payload.json`）。固件在 `upload` 回调里才检查 `payloadCap()`，但 core 在**进入回调之前**已按 `Content-Length` 把整个正文读进一块连续内存。

**②触发条件**
- 非 Chromium 浏览器（Safari、旧 Firefox、部分 Android WebView）或 `new CompressionStream('gzip')` 抛错。
- 长历史：`history_budget=12000` 是**字符**预算，中文 UTF-8 ×3 → 可达 36KB+，加 JSON 结构与提示词后明文 40–60KB。
- 明文 `Content-Length` 逼近或超过当时最大连续块（40–65KB）。

**③代码依据**
- `web/index.html:678` `payloadForm(obj)`：不支持时 `form.append('payload', new Blob([JSON.stringify(obj)]), 'payload.json')`
- core `WebServer/src/Parsing.cpp:347` `char *plainBuf = readBytesWithTimeout(client, _clientContentLength, plainLength, HTTP_MAX_POST_WAIT);`
- core `Parsing.cpp:45-74` `readBytesWithTimeout`：首次 `malloc(newLength+1)`，此后 `realloc(buf, dataLength + newLength + 1)` —— 纯 realloc 增长，**无上限、无连续块校验**，失败返回 nullptr
- `Parsing.cpp:348` 未读满即 `free(plainBuf)` 全丢

**④为什么会爆**
这条路径**完全绕过 `payloadCap()`** —— 上限检查在 `handleUpload` 回调里（`web_server.cpp` upload 分支），而 `plainBuf` 分配发生在更早的 `_parseForm`。堆总量 ~200KB 但最大连续块仅 40–65KB；`realloc` 每增长一步都要找更大的连续块并搬移。即便侥幸分配成功，`plainBuf` 占 M 后，`deserializeJson` 的文档池还要再要一份 ≈2M，必然 OOM。

**⑤后果**
- `realloc` 失败 → 返回 nullptr → `_parseForm` false → 连接被丢弃，前端只看到断连或 500（静默失败）。
- 若解析阶段才 OOM：`doc.overflowed()` 未判 → 把空文档当合法请求发给上游 → 模型答非所问。
- 最坏：堆碎片下 `malloc` 失败被 `HEAP_POISONING_LIGHT` 捕获 → abort → 重启。

**⑥定性**：确认（代码路径与 core 源码一致）。实际浏览器是否走到取决于客户端能力，**未实测**。

## #2 上游请求体与响应体各占一整份堆上 `String`，生命周期重叠

**①现象**
`ollamaChat` / `openaiChat` 都把整包 JSON `serializeJson` 进一个 `String body` 再 `http.POST(body)`；响应侧 `http.getString()` 又把整个响应读进 `String`。两份同时存活。

**②触发条件**
- 任意一次普通提问（非异常路径）：历史越长 body 越大。
- Ollama 非流式（`stream:false`）返回完整答案，可达数 KB 至数十 KB。
- `gpt-oss20b:q8` 长回答叠加长历史。

**③代码依据**
- `ollama_client.cpp`：`String body; serializeJson(doc, body); ... http.POST(body);` 与 `String resp = http.getString();`
- `openai_client.cpp:116` 起 `openaiChat` 同构：`String body` + `getString()`
- `buildMessages`：`m["role"]=v["role"].as<String>(); m["content"]=v["content"].as<String>();` —— 每条历史产生两个临时 String，再写入池内副本

**④为什么会爆**
`String` 按需 `realloc`，每翻倍就要更大连续块。最大连续块 40–65KB 时，`body` 从 32KB 翻到 64KB 这一步就可能失败。`String::concat` 失败后**长度不变、静默不写**，得到的是被截断的 JSON。`resp` 与 `body` 并存时两份都要连续块。

**⑤后果**
- `body` 截断 → 上游 400 → 前端显示后端错误，原因被掩盖。
- `getString()` OOM → 空 String → `deserializeJson` 失败 → 用户看到「回答为空」（静默）。
- 反复 `realloc` 留下堆空洞，最大连续块逐步降到 20KB 以下，连带 gzip 解压也失败（见 #3）。

**⑥定性**：确认（逐行可见）。具体失败阈值受当时碎片影响，**推断**在 32KB 附近首次踩。

## #3 gzip 解压峰值与最大连续块量级不匹配

**①现象**
`upload` 回调只做分块累积，收满后一次性解压到目标缓冲。峰值 ≈ `gzip 体积 + 明文 M + 解压工作区(≈11KB)`，而 `payloadCap()` 与真实连续块脱节。

**②触发条件**
- 明文 M 接近 `payloadCap()`（文档记为 `min(200KB, 最大连续块−24KB)`）。
- 实机最大连续块 40–65KB → cap 应约 16–41KB，但 `docs` 实测记录「150KB 解压后 → 413」，说明 cap 实际取值远大于当前连续块。
- gzip 缓冲本身很小（明文 1.5%–6.5%），压力全在明文缓冲。

**③代码依据**
- `web_server.cpp:8` `#include "miniz.h"`
- upload 分支：`_currentUpload->buf` 为 `HTTP_UPLOAD_BUFLEN` 分块（`WebServer.h:105-114` `HTTPUpload` 结构含 `buf[]`），回调内累积后一次性 `tinfl_decompress_mem_to_mem`
- 413 判定在**解压之后**——`docs/数据流/数据流-内存生命周期.dot` 记录 150KB 解压成功后才返回 413，即证据

**④为什么会爆**
`payloadCap` 里的「最大连续块」是请求开始时测量的运行时量，解压时已变化；且 miniz 需要**一次性 M 连续字节**。M=150KB、连续块 40–65KB 时，中间态必然 OOM 或反复失败。gzip 缓冲 + 明文缓冲 + `JsonDocument` 三份同时在场。

**⑤后果**
- 解压失败 → 400/413（用户可见）。
- `malloc` 失败被 HEAP_POISONING 捕获 → abort → 重启（本次请求全丢）。
- 最坏：解压成功但 150KB 明文进 `deserializeJson`，池再要 150KB → 崩。

**⑥定性**：确认（流程与文档实测一致）。`payloadCap` 在实机的实际返回值**未实测**，公式脱节属**推断**。

## #4 SSE 连接永不关闭 + 前端无 abort → 单连接状态机被占死

**①现象**
core 对 `isSSE()` 为真的连接**永不进入关闭分支**，只在 `HC_WAIT_CLOSE` 里循环重置超时。前端 `ask()` 无 `AbortController`，刷新页面/切会话/断网都无法取消进行中的流。

**②触发条件**
- 一次回答未结束时刷新页面、关闭标签、切 WiFi。
- 板端已写出终止块 `0\r\n\r\n`，但客户端半开（FIN 未到或 keep-alive）。
- 随后任何新请求到达 —— `WebServer` 是单连接状态机。

**③代码依据**
- core `WebServer.cpp:486-491`：`case HC_WAIT_CLOSE: if (_currentClient.isSSE()) { _statusChange = millis(); } // Never close connection`
- core `WebServer.cpp:497-503`：仅当 `!keepCurrentClient` 才 `_currentClient = NetworkClient(); _currentUpload.reset();`
- 前端 `web/index.html:767` `await fetch('/api/chat', {method:'POST', body: form})` —— **无 `signal`**；全文件 `AbortController` 零命中
- 实机依赖 `tools/core-patch-webserver.md`（要求 `chunkResponseBegin` 设 SSE，否则流式失效）——意味着**每次流式回答都会把连接标记为 SSE**

**④为什么会爆**
`WebServer` 只有**一个** `_currentClient` 与 `_currentStatus`（`WebServer.h` 成员）。连接卡在 `HC_WAIT_CLOSE` 且 `isSSE()` 真 → 无限续命 → 新连接排在 `_server` 队列里没人 `accept()`。同时每个存活 `NetworkClient` 持一个 `NetworkClientRxBuffer`，在**首次 `fillBuffer()` 才 `malloc(1436)`**（`NetworkClient.cpp:65`），加 `shared_ptr` 控制块与对象本身约 60B —— 属于泄漏加阻塞。

**⑤后果**
- 一次异常断连 → 后续所有请求无响应（看起来像死机）→ 只能硬重启。
- 若 core 未回收，每残留一条连接泄漏 ≈1.5KB，累计后最大连续块坍缩，连带 #2/#3 一起爆。
- 前端表现为「转圈不动 / 请求超时」，无任何错误提示。

**⑥定性**：core 侧「永不关闭」**确认**（源码注释原文）。是否真死锁取决于客户端 FIN 是否到达，**推断**存在该风险；这是与「重启」关联最紧的一条。

## #5 `fullAnswer` / `answer` / `pending` 三层累积均无上限

**①现象**
流式回答的三处累积串全部没有长度上限：`ollama_client.cpp` 的 `fullAnswer += delta`、`web_server.cpp` 的 `answer` 与 `pending += delta`。在 `chunkWrite` 之前由 `pending` 合并写入的缓冲同样按需增长，且从不检查写入是否失败。

**②触发条件**
- 模型输出长回答：`gpt-oss20b:q8` 单次 4000+ token，中文约 12KB+ 文本。
- 上游卡在循环中重复输出，持续发送 token，直到 `http.setTimeout(65000)` 到期。
- 前端已断开但板端仍在写（与 #4 联动）：`chunkWrite` 返回失败，但循环不会 break（**推断**，取决于 `writeAll` 返回值是否被忽略）。
- 摘要节点 `（此前对话摘要）+ summary` 本身很长，叠进历史后让单次回答起点更高。

**③代码依据**
- `ollama_client.cpp:157` `fullAnswer += delta;` —— 无 cap 判断
- `web_server.cpp:299-300` `String answer; String pending;`
- `web_server.cpp:314` `pending += delta;` —— 每次 delta 都追加，达到长度阈值才 flush（无上界）
- `web_server.cpp:310` `server.chunkWrite(s.c_str(), s.length());`
- `ollama_client.cpp`：`http.setTimeout(65000)` 是唯一时间上界，即最多 65 秒的输出量
- 三处的 `+=` 前后均无 `if (len > MAX) break;` 类判断

**④为什么会爆**
`String::concat` 按需 `realloc`，每次翻倍都要一个更大的**连续块**；而堆最大连续块只有 40–65KB。65 秒 × 局域网吐字速率（20–40 token/s，中文 3B/token）≈ 4–8KB 属正常，但模型循环输出或中英混排长文可到 20–30KB。关键在于**三层同时存活**：`fullAnswer` 在 `ollamaChat` 栈帧、`answer` 与 `pending` 在 `handleChat` 栈帧，总需求约 3×输出量，等于把一个 30KB 输出放大成 90KB 的堆压力。

**⑤后果**
- `realloc` 失败后 `String` **保持旧长度且静默丢弃**后续 `+=` → 用户看到回答「中途截断」，无任何错误提示（最恶劣的静默失败）。
- 若截断发生在 `serializeJson` 阶段 → 上游收到非法 JSON（与 #2 联动），表现为 400 或答非所问。
- `pending` 无上限意味着 `chunkWrite` 的合并缓冲可涨到接近整段回答，等于白白多出一份副本，把 #2 的峰值再抬高一份。
- 大量 `realloc` 在堆上留下空洞，最大连续块逐次缩小，最终连小请求的解析都开始失败（长期劣化）。

**⑥定性**：确认（三处 `+=` 均无 cap 判断，代码逐行可见）。具体在哪个字节数首次失败受当时堆碎片影响，**推断**在输出 20–30KB、三层合计 60–90KB 时进入危险区；`chunkWrite` 失败后循环是否退出**未确认**。

## #6 `buildMessages` 为每条历史构造临时 String，等于历史体积翻倍

**①现象**
`buildMessages` 遍历 `history` 时，对每条消息的 `role` 和 `content` 各调用一次 `as<String>()`，把上游 `JsonDocument` 里的值逐条拷贝进 ArduinoJson 的字符串池，同时产生临时对象；随后 `serializeJson(doc, body)` 再写入第三份。

**②触发条件**
- 每次提问都走这条路径：`history` 由前端按 `history_budget` 组装，长对话时可达 20–40 条。
- 摘要节点 `（此前对话摘要）+ summary` 本身就是一大段文本，前端 `summarizeText` 可累积多轮，作为单条 content 塞进历史。
- 历史总量接近 `history_budget` 上限（12000 字符，中文按 UTF-8 计约 36KB）时最危险。

**③代码依据**
- `ollama_client.cpp` `buildMessages(doc, prompt, history)`：`m["role"] = v["role"].as<String>(); m["content"] = v["content"].as<String>();`
- 调用点：`llm_client.cpp:117-121` → `llmChat(...)` → `ollamaChat(gModelOllama, prompt, history, answer)`
- `openai_client.cpp` 的 `buildMessages` 同构，同样逐条 `as<String>()`
- 上游 `doc` 是整体 `JsonDocument`（非流式写），故 `doc`、逐条临时 String、`body` 三者同时存活
- 全程无 `doc.garbageCollect()`、无预留容量、无 `shrinkToFit()` 之外的释放

**④为什么会爆**
`as<String>()` 在 ArduinoJson 7 里返回一个堆分配的 String 副本，随后 `m["content"] = <String>` 又触发一次池内 strdup。也就是说每条消息的 content 被复制两次（临时 String + 池内副本），`serializeJson(doc, body)` 写入 `body` 是第三次。历史总量为 H 时峰值约 3H + 摘要。H=30KB 时需 90KB，已超总堆的一半，而最大连续块仅 40–65KB。若 `doc` 为动态文档且未预留，池扩容时需整体搬移，要求 2× 池大小的连续块。

**⑤后果**
- 池扩容搬移时找不到连续块 → OOM → `m["content"]` 写入失败，ArduinoJson **静默丢字段** → 上游收到缺 content 的消息 → 400 或答非所问（无法从错误码反查到这里）。
- 每条历史一次 `malloc`+`free`，长对话下持续制造堆空洞，最大连续块逐步坍塌，即使本次请求成功，也为后续请求（#1、#3 的分配）埋雷。
- 与 #2 叠加：H=30KB 时，`buildMessages` 峰值 90KB + `body` + `resp`，几乎是必然的连续失败。

**⑥定性**：确认（代码逐行可见，逐条 `as<String>()` 是明确事实）。`as<String>()` 具体触发两次分配这一细节依据 ArduinoJson 7 语义，**推断**成立；实际每次提问的峰值需用 `heap_caps_get_largest_free_block` 实测才能确认阈值。

## #7 串口 `s_line` 全局累积串无上限，且串口问答阻塞整个 loopTask

**①现象**
`console_ui.cpp` 的 `static String s_line` 逐字符 `+=`，没有长度上限，也没有清空策略；`llm-client.ino` 的 `loop()` 在串口路径上同步执行 `llmChat`，期间 `webHandle()` 无法推进。

**②触发条件**
- 串口终端粘贴长文本（一次几 KB）且不含换行符 → `s_line` 持续增长。
- 串口噪声/波特率不匹配 → 收到乱码字节，永远不形成 `\n`，`s_line` 单调增长直到 OOM。
- 用户从串口提问（`UI_MODE != 1` 分支）→ `llmChat` 内部 `http.setTimeout(65000)` 阻塞，最长 65 秒。
- 串口与网页同时使用：串口问答进行中，网页请求全部挂起。

**③代码依据**
- `console_ui.cpp`：`static String s_line;` + `s_line += (char)c;`（全文件无 `if (s_line.length() > N)` 类判断）
- `llm-client.ino` `loop()`：`#if UI_MODE!=1` 分支内 `String line; if(!uiReadLine(line)) return;` 然后 `wifiEnsure(); llmChat(line, JsonArray(), answer);`
- `loop()` 开头 `webHandle()`，但其后 `llmChat` 是同步调用，帧内不再返回
- 调用链 `llmChat → ollamaChat → http.POST → getString` 全部在 loopTask 栈帧（8KB）内

**④为什么会爆**
`s_line` 是**全局对象，永不释放**，`+=` 每次可能 `realloc` 到更大的连续块；最坏情况单条 String 占满剩余堆，是典型的「全局常驻 + 无上界」泄漏形态。同时 `llmChat` 的调用链上局部对象（`String body`、`String resp`、`JsonDocument doc`、`buildMessages` 的临时 String）全部压在 8KB 栈上；history 数组嵌套解析在树形结构上递归，栈水位随历史长度上升。

**⑤后果**
- `s_line` OOM → 堆被单个全局 String 长期占据 → 后续所有 `malloc` 变慢或失败，表现为「板子跑着跑着变傻」（静默劣化，无错误码）。
- `llmChat` 期间 HTTP 请求 65 秒无响应 → 前端超时 → 用户认为板子已挂。
- 若 JSON 深度在 8KB 栈上递归溢出 → 栈溢出触发 TASK_WDT panic → 重启（有 COREDUMP 到 Flash，用户只看到一次硬重启）。

**⑥定性**：`s_line` 无上限**确认**（代码可见）；串口路径阻塞 Web 处理**确认**（同步调用）。栈溢出属**推断**——代码中无 `uxTaskGetStackHighWaterMark`，未做栈水位实测。

## #8 `Preferences.putString` 每次改配置即写 NVS，磨损与阻塞并存

**①现象**
`llmSetBackend` / `llmSetModel` 每次被调用都立刻 `putInt` / `putString`，无变更检测；前端每次切换后端或模型下拉都触发一次 NVS 写入。

**②触发条件**
- 用户在设置页反复切换后端（ollama ↔ deepseek）或模型下拉，每次都写。
- 前端若在配置保存路径中同步调用写入接口，同一值被重复提交也照写（**推断**，取决于前端是否做去重）。
- `Preferences` 对象常驻不 `end()`，长期持有句柄。

**③代码依据**
- `llm_client.cpp`：`static Preferences gPrefs;`，`llmInit` 中 `gPrefs.begin("llmcfg", false)`
- `llmSetBackend`：`gPrefs.putInt("backend", b)`
- `llmSetModel`：`gPrefs.putString("model_ollama", m)` / `gPrefs.putString("model_deepseek", m)`
- 两处函数开头均无 `if (新值 == 旧值) return;`，全文件无 `gPrefs.end()`

**④为什么会爆**
这不是 OOM，而是**写入放大 + 阻塞**：NVS 每次 `putString` 都要擦除一个 4KB 页、写入、提交，耗时 20–100ms；写入期间 flash 操作会禁用 cache，若执行代码在 flash 上则暂停。默认分区只有 20 个 sector，每次写占用新页，循环使用导致擦写寿命被快速消耗。`Preferences` 常驻对象额外占用少量堆，虽小但属于「永不复用」。

**⑤后果**
- 短时：连续切换模型时每次 HTTP 响应多 20–100ms 延迟，前端有明显卡顿感。
- 长期：NVS 分区磨损 → `getString` 返回默认值 → 后端/模型配置**静默丢失**（用户以为没保存，实际是写坏读空）。
- 极端：擦写失败返回 false 但代码未检查返回值 → 配置「看起来保存成功」而实际未落盘。

**⑥定性**：`putString` 无变更检测、无 `end()`、无返回值检查**确认**（代码逐行可见）。NVS 分区扇区数与擦写寿命属**推断**——未核对 partition 表实际布局。

## 二、它对现有防护的逐条判定 / 建议 / 排序

# 第二部分 A：挑战现有防护

**payloadCap()** — **部分有效**。它只约束在 `handleUpload` 回调中已解压的明文；明文直通路径（core `Parsing.cpp:347` 的 `readBytesWithTimeout`）在回调之前就按 `Content-Length` 分配，完全不经过这道检查，因此它保护的是「解压之后」，而非「分配之前」。

**gzip 上传与 tinfl 解压** — **部分有效**。gzip 确实把上传体积压到原来的 1.5%–6.5%，但解压仍是**一次性全量**（`tinfl_decompress_mem_to_mem`），峰值仍需 M 字节连续内存；它节省了网络栈，却没有节省堆。

**零拷贝解析** — **形同虚设**。`buildMessages` 里 `v["role"].as<String>()` / `v["content"].as<String>()`（`ollama_client.cpp`）把每条消息复制到临时 String，再复制到池内，`serializeJson` 写 `body` 时再复制一次——历史总量 H 对应峰值约 3H，「零拷贝」只存在于前端到板端的传输层。

**releasePlain()** — **有效但有时序风险**。它能在解析后及早归还明文缓冲，但必须保证所有指向它的指针都已失效；若 SSE 流程中仍持有片段引用（`parseSsePayload` 的 `payload` 指向明文内部），提前释放会造成 use-after-free。属于「用对了就省内存，用错就是堆破坏」。

**readPayload() 的 413/400** — **部分有效**。错误码明确、用户可见，但 413 的判定在**解压之后**（`docs` 实测 150KB 解压后才返回 413），即「先花掉峰值内存，再告诉你不该来」。它防住了错误继续传播，却没防住错误本身。

**chunkWrite 的 64 字符合并** — **有效**。合并小写显著减少 TCP 分组与 `write()` 调用开销，缓冲固定 64 字节，不随回答增长。上限明确、行为可预测，是本清单里少有的「没有副作用」的优化。

**SUMMARY_INPUT_MAX 截断** — **部分有效**。它在 `/api/summarize` 入口截断输入，防止摘要请求本身爆堆；但前端 `summarizeText` 会先累积「已有摘要 + 新增历史」再发送，累积阶段在浏览器侧不受此限，板端只是最后一道闸门。

**WiFiClient/WebServer 超时** — **部分有效**。`http.setTimeout(65000)` 给了上游硬上限，`HTTP_MAX_POST_WAIT`、`HTTP_MAX_DATA_WAIT`、`HTTP_MAX_CLOSE_WAIT` 覆盖了常规等待；但 `isSSE()` 分支会无条件重置 `_statusChange`（`WebServer.cpp:486-491`），使 `HTTP_MAX_CLOSE_WAIT` 对 SSE 连接**完全失效**——超时机制在流式路径上自相矛盾。

**Preferences(NVS) 配置** — **部分有效**。它确实持久化了配置，但 `llmSetBackend`/`llmSetModel` 每次调用即写（无变更检测），每次 `putInt`/`putString` 都要擦写 4KB 页，并在 20–100ms 内阻塞；防丢配置，却以磨损与延迟为代价。

# 第二部分 B：建议改法与代价

### 改点 1：给明文路径加上「分配前上限」

**改什么**：在 `handleUpload` 拿到 `totalSize` 后立即判 `> payloadCap()` 就返回 413 并中止；同时在 core 侧或 `canRaw` 钩子里拦截未走 multipart 的 POST（`Content-Length` 超阈值直接 `return false`）。等价做法是在 `webBegin` 里注册 `server.onNotFound` 前置拒绝，但更稳的是改 `_parseForm` 的调用点。
**文件**：`web_server.cpp`（上传前置判定）、`tools/core-patch-webserver.md` 对应的 core 补丁（`Parsing.cpp` 加 `_clientContentLength` 早期检查）。
**行数**：应用侧约 10–15 行；core 补丁约 8–12 行。
**Flash/RAM 代价**：几乎为零（只剩几个 `size_t` 比较）。
**风险**：低。唯一注意是别把 gzip 分块的总字节数误当明文大小——必须在 `HTTPUpload::totalSize` 或已解压明文长度上判，不是在分块序号上判。
**值不值得**：**值得，优先级最高**。把 #1 的整条 OOM 路径变成一次干净的 413。

### 改点 2：`body` / `resp` 改为流式，不复用整包 String

**改什么**：`ollamaChat` 的请求体用 `http.sendRequest("POST", &stream, len)` 或直接 `serializeJson(doc, http.getStream())`（`HTTPClient` 的 `Print&` 重载），避免 `String body` 整包落地；响应侧用 `http.getStream()` + 行读取解析，替代 `getString()`。
**文件**：`ollama_client.cpp`、`openai_client.cpp`。
**行数**：每处约 25–40 行改造（原为 `serializeJson` + `POST` + `getString` 三段式）。
**Flash/RAM 代价**：Flash +约 1–2KB；RAM **省** 1–2 份 M。
**风险**：中。`HTTPClient::getStream()` 在 chunked 响应下要自己处理分块边界；`serializeJson(doc, Print&)` 仍会逐块写但需要保证 `doc` 已完全构建（这本身也是 #6 的痛点）。改错了会表现为「上游收到半截 JSON」。
**值不值得**：**值得，第二大**。这是 #2 的根因，而 #2 是每条请求的必踩路径。

### 改点 3：去掉 `buildMessages` 的逐条 `as<String>()`

**改什么**：直接遍历上游 `history` 的 `JsonArray`，边遍历边把 `role`/`content` 以 `const char*`（`as<const char*>()`）写入目标 `doc`，避免每次 `as<String>()` 生成临时 String。
**文件**：`ollama_client.cpp`、`openai_client.cpp` 的 `buildMessages`。
**行数**：约 10–15 行。
**Flash/RAM 代价**：Flash 几乎无变化；RAM 省下每条消息一个临时 String（H 场景下省约 1/3 峰值）。
**风险**：低。`as<const char*>()` 在 ArduinoJson 7 里对 `String` 类型的源会返回内部指针，目标池仍需 `set()` 复制一次——但省掉的是**中间那份**，语义不变。
**值不值得**：**值得，和改点 2 顺手一起做**。

### 改点 4：给 SSE 连接加「客户端可取消 + 服务端超时」

**改什么**：前端 `fetch` 加 `AbortController`，`ask()` 开始时创建、`finally` 里 `abort()`；板端在 SSE 主循环里检测「`chunkWrite` 连续 N 次写失败 或 `millis()` 超总预算」就主动 `server.client().stop()`。若 core 补丁可控，另在 `HC_WAIT_CLOSE` 的 `isSSE()` 分支里加一个独立于 `_statusChange` 的硬超时（比如 30s 后强制关）。
**文件**：`web/index.html`（约 8 行）、`web_server.cpp`（约 10 行）、core 补丁（约 6 行）。
**Flash/RAM 代价**：极小。
**风险**：中。硬关连接可能在正常长回答中途掐断（需把硬超时设得比最长回答宽松，如 120s）；前端 `abort()` 会触发 `fetch` 的 `AbortError`，需在 `catch` 里静默忽略，否则会弹错误气泡。
**值不值得**：**值得**。#4 是唯一会让整机「看起来死掉」的路径，成本却很低。

### 改点 5：`Preferences` 加变更检测

**改什么**：`llmSetBackend` / `llmSetModel` 开头先比对当前值，相等直接 `return`。
**文件**：`llm_client.cpp`。
**行数**：约 6 行。
**Flash/RAM 代价**：可忽略。
**风险**：极低。
**值不值得**：**值得**，但属「顺手修」，不必单独排期。

# 第二部分 C：排序

## 最危险的 3 条

**#1 明文路径整包 `realloc` 进堆** — 因为它是**唯一完全绕过 `payloadCap` 的分配路径**，一旦踩中就是 `realloc` 失败 + 静默断连，或 OOM abort 重启，且触发条件（非 Chromium 浏览器 / 长历史）在真实使用中很常见。

**#4 SSE 连接永不关闭 + 前端无 abort** — 因为它是**唯一能让后续所有请求永久无响应**的路径；单连接状态机一旦卡在 `HC_WAIT_CLOSE`，若不硬重启就无法自愈，且用户看到的是「板子死了」而非「请求失败了」。

**#2 `body` + `resp` 双份整包 String** — 因为它是**每次提问都必踩**的路径（不是异常分支），峰值 2M 与历史长度线性相关；失败的形态是「回答静默截断」或「答非所问」，排查成本最高。

## 如果只改 1 处

**改 #1 的前置上限判定**（第二部分的改点 1）。理由：它是唯一能用 10 行代码、零 RAM 代价，把「不可控 OOM」变成「可控 413」的改动；#2 和 #3 的爆堆都需要一定历史长度才踩，而 #4 的卡死至少还能靠断电恢复——只有 #1 是**在任何一次明文请求都可能踩，且踩中就会重启或静默失败，并且没有任何错误码能告诉用户发生了什么**。

## 虽然是风险但不必改的

- **`parseSsePayload` 每事件新建 `JsonDocument`** — 每个 SSE 事件的生命周期极短，栈上或小池的对象会被立即复用，实际碎片贡献远小于 #6 的逐条 String；改它收益不抵改造风险。
- **`secureClient` 用 `setInsecure()`** — 这是**安全**取舍，不是内存问题；省掉的 mbedtls 证书缓冲（约 4–6KB）反而对内存有利。真要改应作为独立的安全议题处理。
- **前端 `saveState()` 每次流式都 `JSON.stringify` 整状态** — 消耗的是**浏览器**内存，跟板子堆无关；只在会话极长时才有感知，属浏览器侧优化，不进板端清单。
- **`marked.min.js` 35KB 与前端 DOM 增长** — 同样是浏览器侧，且 `marked.parse` 的峰值随单条回答长度而非会话长度增长，可接受。
- **`s_line` 无上限（#7 的一半）** — 只在串口噪声或粘贴超长文本时触发，正常使用不会走到；加一行 `if (s_line.length() > 512) s_line = ""` 顺手做即可，不值得单独立项。

### 决定：单线程排队窗口不再改动（2026-11-01，用户拍板）

上面第一条残留**保持现状，不再投入**。评估过的三个方案记录在此，供以后回看时直接引用，
不必重新论证：

| 方案 | 改动量 | 效果 | 结论 |
|---|---|---|---|
| A. 流式读取改轮询（阻塞读 → 200ms 一段 + 每段查 `shouldStop`） | `http_stream.h` 约 20 行 | 客户端断开后 200ms 内释放上游，不再干等下一行或 300s idle | **不做** |
| B. core 让 `chunkWrite` 返回 bool | 第三个 core 补丁 + 应用侧几行 | 只能抓"写失败"，抓不到主因（阻塞在等上游） | **不做** |
| C. 流式搬到独立任务 | 新建 task + 处理 WebServer 并发（`_currentClient`/`_currentStatus` 非线程安全，+8KB 常驻栈） | 才能让"一次生成阻塞所有请求"彻底消失 | **不做** |

理由：收益只在"模型正在生成时用户手快刷新/开新标签"这个窄场景，而真问题是模型吐字慢；
为此去动最热的流式路径或重构并发模型不划算。

**现状与后果（接受）**：
- 流式期间新请求排队，等待时长 ≈ 模型本轮生成时长（实测一例 102 秒）；
- `streamLines` 的 idle 超时保持 300 秒；
- 客户端断开仍能被发现（`shouldStop` 生效），只是要等上游吐下一行才检查到。
