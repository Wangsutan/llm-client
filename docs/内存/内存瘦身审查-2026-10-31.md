# 内存瘦身方案审查报告

- 审查方：`.20` 智能体（DeepSeek 模型）
- 审查对象：ESP32 局域网大模型客户端的内存流程优化
- 日期：2026-10-31

> **后续更新（2026-11-04 补）**：本文记录的是 2026-10-31 当时的状态。该文档之后，
> #2（serializeJson 直接写 socket）、#3（chunked 逐条序列化）、#4（gzip 流式）与
> 11-01 的静态工作区（48 KB，明文不经过堆、就地零拷贝解析）已全部实施；
> 当前请求期堆占用实测只 +2–3 KB（TLS/WebServer 开销），历史全量在静态区只存 1 份。
> 正文中的「8 份副本 → 4 份」与 4M 峰值均为**历史口径**，不代表当前实现
> （当前见 `docs/开发/对话长度与内存上限-2026-11-04.md` 与 `docs/内存/内存实测-探针-2026-11-01.md`）。

## 背景

ESP32-D0WD-V3（4MB Flash、520KB SRAM，可用堆 ~200KB，流式时 ~100-140KB）。
网页聊天链路：浏览器 fetch → WebServer（POST /api/chat）→ 转发 Ollama/DeepSeek → 流式回传。
请求体 `{"message":..., "history":[...]}`，完整历史可达数万字符（M 字节）。

## 当前已做优化（8 份副本 → 4 份）

1. history 以 JsonArray 直接传递，去掉序列化/再解析中转（省 2-3 份）
2. 请求体 body 解析后立即出作用域释放
3. HTTP 请求分两次 write，不把 body 拼进大 String
4. buildMessages 直接遍历 JsonArray

当前峰值 ≈ 4M（WebServer 内部 `_currentArgs` + `in` 文档 + `messages` 文档 + 上游请求体 String）。

## 审查建议（按收益排序）

| # | 做法 | 预计省 | 代价/风险 | 状态 |
|---|---|---|---|---|
| 1 | 前端 Blob 伪文件 multipart + 后端 upload 回调流式累积（文本字段会进 _currentArgs，必须用带 filename 的文件字段） | ~M | 低风险（实测通过） | **已实施**（2026-10-31） |
| 2 | `serializeJson(doc, client)` 直接写网络（measureJson 算长度），上游请求体不落地 String | ~M | 低风险；实测写入字节数校验 | **已实施** |
| 3 | 不建 messages 全量数组：逐条序列化 + chunked 请求体（单条临时文档，转义仍由 ArduinoJson 负责） | ~M | 低风险（实测通过） | **已实施**（2026-10-31） |
| 4 | 前端 gzip + 板端流式 inflate（解压窗口 ~32KB） | M→1/3~1/4 | 需 inflate 库（Flash），流式解压实现 | 待评估 |
| 5 | `shrinkToFit()` + history 超限 `remove()` | 5-15% | 无风险 | 未做 |
| 6 | Filter 去无关字段 / MsgPack | 5-10% | 前端改动 | 未做 |
| 7 | 下载侧栈上 512B 缓冲 + 残留行缓冲 ≤256B | 固定 1-2KB | 无风险 | 未做 |

**关键判断**：#1+#2+#3 全做可 4M→1M；再加 #4 gzip 等效 M 降到 ~30-40KB，彻底安全。

## 实施建议（原审查意见）

1. 先做 #2+#3（纯后端，风险最低）
2. 再做 #1（动前端表单，收益最大，但需流式 JSON 解析器）
3. 最后评估 #4（gzip，可把上限再翻 3 倍）

## 本次落地记录

- 已实施 #2：流式请求不再序列化到 String，`measureJson` 算 Content-Length 后
  `serializeJson(doc, client)` 直接写入 socket，省一份 M。
- #1 已实施：前端用 Blob（filename）上传走 upload 回调，后端分块累积 payload，省掉 WebServer 的 _currentArgs 副本；curl -F 与浏览器端到端均验证通过。
- #3 已实施：请求体改为 chunked（Transfer-Encoding: chunked），messages 逐条序列化发送，不再建全量数组；chunked 请求体已确认 Ollama/DeepSeek 均支持；多轮记忆回归通过。
- #4 已实施（gzip）：前端用 `CompressionStream('gzip')` 压缩请求体，文件名带 `.gz` 后缀上传；
  后端在 upload 回调结束时解压。实测 6104 字节历史压缩到 396 字节（6.5%）。
  踩坑与做法：
  - 只有 ESP32 ROM 里的 `tinfl` 可用（classic ESP32 的 esp_rom `miniz.h` 带
    `MINIZ_NO_ZLIB_APIS`，没有 zlib 风格 API；GitHub 上 miniz 2.x/3.x 是多文件版本，
    塞不进 sketch）。
  - `tinfl_decompress_mem_to_mem()` 内部把 ~11KB 的 `tinfl_decompressor` 放在栈上，
    而 loopTask 栈只有 8KB → 实测直接 `Guru Meditation: Stack canary watchpoint` 重启。
    改为堆上 malloc 解压器 + 直接调 `tinfl_decompress()`。
  - 解压结果用 malloc 缓冲保存，`deserializeJson(doc, buf, len)` 就地零拷贝解析
    （不再复制一份 M 的正文到 String，省一份 M），缓冲留到本轮结束随请求释放。
  - 压缩数据在解压后立即释放，峰值 ≈ gz(M/3) + 明文(M) + 解压器(11KB)，比明文上传的
    String+文档 2M 还低。
- #5/#7 为低风险小优化，可后续分批做（做完 #1–#4 后评估：收益已很小——#5 省的
  是文档池里的零星余量、且与前端"按预算保留 + 摘要压缩"逻辑重复；#7 只改善堆碎片，
  省固定 1–2KB。故暂不做）。

## 验证

实施 #2 后：编译通过、浏览器端流式回答正常（多轮上下文回归通过）。

实施 #4 后（固件 1,134,548 字节 / 86%）：
- `python3` 直接构造 gzip multipart（`payload.json.gz`）→ HTTP 200 流式回答正常；
- 10 轮历史（6104 字节 → 396 字节）多轮记忆回归通过，模型能正确总结上文；
- `.20` 上 headless Chromium 跑真实页面：`CompressionStream` 可用，实际上传分片名为
  `payload.json.gz`，回答正常渲染；
- 浏览器不支持 `CompressionStream` 时回退上传明文 `payload.json`，后端两条路径都验证过。

### 后续加固：payload 上限对剩余堆敏感（固件 1,135,900 字节 / 86%）

实施 #4 时发现原解压长度上限写死 200KB，比可用内存还大（实测空闲堆 ~200KB，但最大
连续可分配块只有 40–65KB）：中文历史真打满 40000 字符预算时 `malloc` 失败会退回
`{"error":"bad json"}`，用户只看到莫名其妙的失败。

- `payloadCap() = min(200KB, 最大连续可分配块 - 24KB)`（24KB 给 tinfl 解压器与解析/流式留余量）；
  预算在 `UPLOAD_FILE_START` 定一次——累积时 payload 自己也在吃堆，实时算会把上限压到一半。
- 写入前先判断再 `concat`（String 越界增长会静默截断，不能靠它兜底）。
- gzip 拆成 `gzipParse`（解析头与 ISIZE）+ `gzipInflate`，先看解压后多大再决定是否 malloc。
- 超限回 `413 {"error":"payload too large","code":"payload_too_large"}`，网页显示中文提示
  "历史太长，板子内存放不下；请新建会话，或把问题缩短一些再试"。

实测：明文 45KB 通过（162 条历史，回答正常）、明文 150KB 与 gzip 解压 150KB 均 413、
正常 6KB 与 gzip 6KB 仍 200；`.20` headless Chromium 拦截 413 后界面文案与正常发消息都验证过。

### 后续加固：堵掉 `/api/summarize` 的复制后门（固件 1,135,884 字节 / 86%）

`payloadCap()` 只保护 `/api/chat`，而 `/api/summarize` 走的是"直接 POST JSON body"的老路：
`WebServer` 先用 `readBytesWithTimeout()` 把整个 body malloc 下来，再 `arg.value = String(plainBuf)`
复制进 `_currentArgs`，然后 `server.arg("plain")` 再拷一份、`deserializeJson` 又拷一份、
`as<String>()` 还拷一份 —— 而 `SUMMARY_INPUT_MAX` 的截断发生在**所有副本都产生之后**。
峰值约 4×body，且只在"对话长到开始丢轮次"时触发，正是内存最紧张的时刻。

- 后端：把 `/api/summarize` 接进和 `/api/chat` 同一条上传管线（`server.on(..., handleSummarize,
  handleUpload)`），新增 `readPayload()` 统一处理"gzip 就地解析 / 明文 multipart / 413 / 400"；
  摘要文本改成**先 `strnlen` 限长再复制**（最多 `SUMMARY_INPUT_MAX` 字符），请求结束立刻
  `releasePlain()`。
- 前端：抽出 `payloadForm()`，聊天和摘要都用"gzip + 带 filename 的 payload 字段"上传。
- 直接发 JSON body 的旧用法现在返回 `400 {"error":"multipart payload required"}`（有意为之：
  那条路正是要堵的坑）。

实测：summary gzip 6KB → 200 且摘要正确；明文 multipart → 200；解压后 150KB → 413
`payload_too_large`；聊天回归 200；`.20` headless Chromium 真实页面把预算压到 60 字符后，
第 3 轮自动触发 `/api/summarize`（上传分片 `payload.json.gz` 172 字节），摘要写回会话、
后续提问仍能答出上下文，无 pageerror。

### 后续加固：请求工作区改为静态分配（2026-11-01，固件 1,137,200 字节 / 86%）

问题不在"堆总量不够"，而在"能一次 malloc 出来的连续块不够"：实测空闲堆约 200KB，但最大
连续块只有 40–65KB 且随碎片浮动，所以 `payloadCap()` 只能用 `maxAllocHeap() - 24KB` 动态估算，
上限忽大忽小，短请求也在反复制造/打碎大块。

改法（静态工作区）：
- `llm_limits.h` 新增 `WORK_BUF_SIZE = 48KB`；`web_server.cpp` 里 `static char g_work[…]` 放 `.bss`，
  地址固定、开机即占、每轮不再 malloc；
- 解压器 `tinfl_decompressor`（11KB）同样改为 `.bss` 常驻，不再每轮 malloc/free；
- 明文上传**直接累积进工作区**（省掉中间那份 `String` 副本）；gzip 上传先用小 String 接压缩数据，
  再解压进工作区；两种路径最后都在工作区里就地零拷贝解析；
- `payloadCap()` 变成常量 `WORK_BUF_SIZE - 1KB = 48,128` 字节，413 阈值可预测。

代价与收益：

| 项 | 改前 | 改后 |
|---|---|---|
| 全局变量（.data+.bss） | 49,584 B（15%） | **109,736 B（33%）** |
| 留给堆 | 278,096 B | 217,944 B |
| 空闲堆（实测） | ~200KB | ~154KB |
| 单请求明文上限 | 动态 16–41KB（随碎片） | **固定 48,128 B** |
| 每轮大块 malloc | 2 次（明文 + 解压器） | **0 次** |

实测：gzip 小请求 200；明文 45,189 B → 200（37.6s）；明文 60,175 B → 413；gzip 解压后
102,459 B → 413；10 轮历史 200；`/api/summarize` 200；`.20` headless Chromium 页面聊天正常；
连发 8 轮 `heap` 依次 154852 → 153444（无单调下降趋势，不再有大块 churn）。

已知取舍：中文约 16,000 字就是上限（48KB ÷ 3），低于 40000 字符的预算，超了就是可预测的 413 +
前端提示。想抬上限只需改 `WORK_BUF_SIZE` 一个常量（例如 64KB → 约 21,000 字）。

### 后续加固：板子不再保存回答全文（2026-11-01，固件 1,137,548 字节 / 86%）

之前模型吐的每一段在板上被攒两份：`ollamaStream`/`openaiStream` 里的 `fullAnswer` 和
`web_server` 里的 `answer`，各 64KB 上限，最坏 128KB —— 而空闲堆只有 154KB，且这两份谁都不用
（完整文本已经在浏览器里）。最紧的场景（DeepSeek + mbedtls 32–40KB 连续块）因此很容易顶穿。

- `llm_limits.h` 新增 `LLM_KEEP_MAX = 2048`：板上只保留回答前缀；
- `ollamaStream`/`openaiStream`/`llmStream` 新增 `size_t* totalBytes` 出参，用计数器统计总字节数，
  超长判断改成看计数（`total >= LLM_ANSWER_MAX` 就停），返回值和日志也用计数；
- `web_server` 删掉重复的 `answer += delta`，截断提示改看 `answerBytes`；
- 摘要接口仍用前缀（提示词要求摘要不超过 200 字，2KB 足够）；
- 顺手把 `uxTaskGetStackHighWaterMark(NULL)` 打进日志（`chat` 与 `done` 两行），把栈余量从
  反汇编推算变成实测。

收益：最坏堆占用从 ~128KB 降到 ~4KB。实测：短回答 48 B → `kept 48`；长回答浏览器收到 2,929 B、
板上 `kept 2048`；把上限临时改成 200 字节仍能正确输出"（回答超过长度上限，已截断）" + `done`；
`/api/summarize` 200；连发 6 轮 chat 起始堆恒定 154,764 B。

栈水位实测：chat 期间 `stack left` 稳定 4,956 B，即 loopTask 峰值只用了约 **3.2KB**（8KB 栈还剩
62%），6 轮无增长。
