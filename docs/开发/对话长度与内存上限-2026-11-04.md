# 对话长度与内存上限：多长的对话会把板子顶爆（2026-11-04）

## 背景

项目在早期用「历史全量保存 + 每次请求把完整历史序列化」的朴素方式，最大连续块和空闲堆
会被对话长度逐渐啃穿。后来做了多层优化（静态工作区、gzip 流式、预算 + 摘要），
本文把「不做调优会怎样、现在为什么安全、还剩哪些边界」整理成可查的口径。

**数据来源**：`docs/内存/内存实测-探针-2026-11-01.md`（memprobe 实测）、
`docs/内存/内存瘦身审查-2026-10-31.md`（各阶段副本数变化的历史记录：8 份 → 4 份 → 当前约 1 份）、
`llm_limits.h`（常量）、`web/app.js`（`buildMessages` 的预算/摘要逻辑）、
`secrets.h`（历史预算）。

## 一、内存基线（实测）

| 项 | 数值 | 说明 |
|---|---|---|
| 空闲堆（复位后、首轮请求前） | **155,408 B** | `getFreeHeap()`，相对 `getHeapSize()` 262,236 |
| 最大连续块 | **110,580 B** | 单次分配超过它就必失败（隐形硬墙） |
| 请求期可用余量 | 约 100–140 KB | 流式期间 |
| 链接期 DRAM 堆段 | 161,784 B | 内存分布图口径；不等于运行期可用堆 |

注意 `getFreeHeap()` 是相对 **262,236**（DRAM 222,152 + IRAM 40,084）算的，不是 161,784——
后者是「`.bss` 之后到 DRAM 末尾」的静态段口径。

## 二、不做调优时的爆点估算

朴素实现：对话历史全量保存、每次请求把完整历史序列化成 JSON String、不截断不摘要不压缩。
以下按审查报告 2026-10-31 时的中间状态估算（当时 4 份副本：WebServer 参数副本 + 解析文档 +
转发文档 + 请求体 String；更早的重构前是 8 份。**当前实现已远低于此**——静态区 1 份明文 +
逐条序列化小缓冲，堆上 0，见第三节）。

| 对话内容 | 每轮体积 | 估算崩溃点 |
|---|---|---|
| 短问答（"hi"级） | ~150 B | 150+ 轮才接近上限，实际对话到不了 |
| 一般中文对话（问 50 字 + 答 400 字） | ~1.5 KB/轮 | **约 15–20 轮**（约 6,000–10,000 字历史）开始失败 |
| 一般英文对话（答 800 字符） | ~0.9 KB/轮 | 约 30–39 轮 |
| 长回答（答 1,000 字 ≈ 3 KB/轮） | ~3 KB/轮 | **约 8–12 轮**就爆 |
| 半调优（解析后直接序列化，少 2 份拷贝） | 同上 | 约 30–40 轮（单块 110 KB 限制约 18,000 字先到） |

*含 JSON 结构开销（`{"role":"user","content":"…"}` 约 40 B/条）。

**为什么是这个量级**（按朴素 4 份拷贝估算）：4 × 历史字节数；历史超 ~35 KB 就撞
100–140 KB 可用余量；单块 110 KB 上限让「2 份拷贝」方案在历史 JSON 超 ~55 KB 时也在
单次分配处失败。历史口径不代表当前实现（当前历史全量只在静态区 1 份）。

**爆的方式**：`malloc` 返回 null → 请求回 500/413 或 JSON 解析失败（通常不死机，
只是请求失败；极端情况——忽略 null 继续拼接——可能触发看门狗/重启）。

## 三、当前实现为什么安全

1. **请求体长度有界**：前端按模型做历史字符预算（qwen3 15,000 / 20b 40,000 / deepseek 25,000，
   `secrets.h` 的 `HISTORY_BUDGET_*`），从最近往前保留完整轮次，超预算的早期轮次压缩成摘要
   （`/api/summarize`，缓存到会话 `conv.summary`）；发给模型的是「摘要 + 最近保留轮次」，
   **总字符数 ≤ 预算 + 摘要长度，与对话轮数无关**。
2. **请求期堆占用是常数**：实测一次请求只 +2–3 KB（明文落 48 KB 静态工作区 `WORK_BUF_SIZE`，
   解压/解析不在堆上，gzip 后请求体约 6.5%）。
3. **回答有上限**：`LLM_ANSWER_MAX = 65,536`（防长回答啃穿连续块）；板上只保留回答前
   2 KB 前缀（`LLM_KEEP_MAX`）。
4. **摘要长度可控**：摘要提示词要求 ≤ 200 字，板子端 `LLM_KEEP_MAX` 2 KB 兜底。

## 四、还剩的边界（不会崩，但会显式失败）

| 边界 | 行为 |
|---|---|
| 单条超长消息（首条就超预算） | `kept.length > 0` 保护下会整条发出 → 板子 `payloadCap` 兜底回 **413 `payload_too_large`**，前端提示「历史太长」 |
| 摘要请求本身 | 摘要要把被丢弃的早期历史上传，同样受 48 KB 上限；失败时前端只丢远期上下文、聊天继续（catch 兜底） |
| 摘要长度 | 由提示词 + `LLM_KEEP_MAX` 限制，不会无限增长挤占预算 |
| 换设备 / 清 localStorage | `conv.summary` 丢失 → 从头累积再压缩，功能正常、上下文变短 |

**真正的「顶爆」风险已经从「对话长度」转移到「单次请求处理」**（48 KB 工作区 + 回答上限），
与聊了多少轮无关。

## 五、结论

- **对话再长也顶不爆了**：摘要 + 预算把请求封顶，内存占用与对话轮数无关。
- 会顶的是「单条消息或单次请求太大」——显式 413 报错，不是崩溃。
- 若想压测确认：把 `history_budget` 临时调大做长对话实验即可观察上限（不建议常开）；
  正常使用下无需担心。
