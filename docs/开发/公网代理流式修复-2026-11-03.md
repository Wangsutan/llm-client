# 公网代理流式修复记录（2026-11-03）

> 现象：手机（安卓 Firefox）经公网 `http://203.0.113.10:8090/` 访问板子页面，
> 回答不再流式，一直显示 "Thinking"，最后一次性出现；局域网直连正常。

## 一、查证

| 测试 | 结果 |
|---|---|
| 直连板子 192.168.1.50:80（curl） | 流式正常：每 0.5–1s 一块 |
| Chromium 直连 | 流式正常 |
| Playwright Firefox 直连 | 流式正常（文本 8→24→…→145 逐步增长） |
| 公网 8090 | 一次性（1 块） |

链路：`公网 203.0.113.10:8090 → frps → frpc（局域网主机） → 127.0.0.1:8099 proxy.py → 板子:80`
（`.10` 用户级 systemd：`esp32chat.service`，脚本 `~/esp32chat/proxy.py`）

## 二、根因

`proxy.py` 流式转发用的是 `http.client` 的 **`resp.read(CHUNK)`（CHUNK=8192）**：
`read(n)` 会**阻塞直到读满 n 字节或连接关闭**。聊天响应很小（约 1 KB < 8 KB），
于是代理等到上游响应结束才第一次写出 → 浏览器一次性收到 → "一直 Thinking，最后一次性出现"。

## 三、修复

代理转发读取改为 **`resp.read1(...)`**（有数据即返回、不等待凑满 n 字节）：

- Content-Length 分支：`resp.read(min(CHUNK, remaining))` → `resp.read1(...)`
- chunked 分支：`resp.read(CHUNK)` → `resp.read1(CHUNK)`

已同步两处：`.10:~/esp32chat/proxy.py`（部署副本，重启 `esp32chat.service` 生效）
与仓库 `tools/esp32chat-proxy/proxy.py`。

## 四、验证（修复后，经公网 8090 + Basic 认证）

11 个 chunk 在 7.84s–13.71s 之间**分批到达**（每块 61–83 B），与直连板子一致。
局域网直连不受影响。
