# 编译优化记录（2026-11-03）

> 起因：用户询问能否通过编译优化改善固件/内存占用。实测了几组编译选项，
> 结论：`-flto` 在 ESP32/xtensa 上不可用（core 官方禁用），`-fno-exceptions` 组合可用，
> 落地后 flash 减 2.9%，RAM 几乎不变。

## 一、-flto：不可用（官方禁用）

- ESP32 core 3.3.12 的链接 flags（`esp32-libs/3.3.12/flags/ld_flags`）**显式带 `-fno-lto`**。
- 强行用 `--build-property` 打开 LTO 后链接失败：
  `dangerous relocation: windowed longcall crosses 1GB boundary; return may fail`
  （发生在 core 的 `esp32-hal-misc.c`，是 Xtensa 1GB 长调用窗口与 LTO 的冲突）。
- 结论：不要再用 `-flto`，这是 xtensa 架构限制 + core 主动关闭。

## 二、实测数据

基线 = 无 build_opt.h（-Os）：固件 1,133,488 B，globals 109,760 B。

| 编译选项 | 固件大小 | 变化 | globals |
|---|---|---|---|
| 基线 | 1,133,488 B | — | 109,760 B |
| `-fno-exceptions` | 1,101,456 B | −32,032 B（−2.83%） | 109,760 B |
| + `-fno-threadsafe-statics` | 1,100,672 B | −32,816 B（−2.89%） | 109,744 B |
| + `-fno-unwind-tables -fno-asynchronous-unwind-tables` | 1,100,672 B | 同组合 | 109,744 B |
| + `-fmerge-all-constants` | 1,100,672 B | 无变化 | 109,744 B |
| + `-fno-math-errno` | 1,100,672 B | 无变化 | 109,744 B |

- `-fno-exceptions` 是主力（约省 31–32 KB），`-fno-threadsafe-statics` 再省 784 B；后两项在 -Os 下无贡献。
  组合行在不同构建里有 ±150 B 的摆动（-Os 下内联布局差异），**最终落地实测 1,100,516 B**。
- 链接的 `-Wl,--gc-sections` 是 core 默认已开，没有额外空间。
- **RAM 基本无收益**（globals 只 −16 B）：RAM 大头是结构性的（payload 48 KB 工作区、
  tinfl 解压器 ~11 KB、TLS 上下文、core 网络缓冲），不属于编译选项能解决的范畴。

## 三、落地：build_opt.h

仓库根目录新增 `build_opt.h`（arduino-cli 自动识别，`tools/build.sh` 无需改动）：

```
-fno-exceptions
-fno-unwind-tables
-fno-asynchronous-unwind-tables
-fno-threadsafe-statics
```

固件：1,133,488 → **1,100,516 B**（86% → 83%，−32,972 B）；globals 109,760 → 109,744 B。

## 四、验证

- **编译**：通过（arduino-cli，esp32 core 3.3.12，default 分区）。
- **烧录回归**（板子 IP `192.168.1.50`，`.21` 串口抓 IP + curl，10/10 通过）：
  静态页、marked.min.js、config、models、chat（gzip/明文）、summarize、空 message 400、
  坏 JSON 400，串口日志 `[http] stream end: normal`。

## 五、风险与注意

- 项目代码不用 try/catch；ESP32 的 `new` 失败返回 `nullptr`（不抛）；ArduinoJson 用返回码
  （均检查）。剩余风险是极小概率的库内部异常会直接 abort（panic），正常路径不触发。
- 选项对整个编译单元生效（含第三方库头文件内代码），与 core 预编译库混合链接正常。
- 如需进一步减小：只能动结构（如 payload 工作区 48 KB 调小，需评估最大请求体）或换分区表
  （huge_app 等只改百分比，绝对大小不变，且要同步改 `tools/build.sh` 的 LittleFS 偏移）。
