# payload 模块审核修复（2026-11-02）

> 起因：用户对 `payload.cpp`（请求体管线）给出三条审核意见：
> ① 错误分类全归 413；② 溢出检查用和式；③ XLEN 越界只看 `off + 2`。以下逐条修复。

## 一、错误分类：413 只留给"真超限"

原实现里 `g_uploadError` 是裸 `const char *`，`payloadRead()` 对任何非空错误都回
`413 {"error":...,"code":"payload_too_large"}`——坏 gzip、空包也被归成内存超限，
客户端拿到的错误码指导不了下一步。

改为上传回调里记下 `{文案, http, code}`（`struct UploadReject`），`payloadRead()` 按记录回：

| 情形 | 状态码 | code |
|---|---|---|
| 明文 / gzip 超过工作区预算 | 413 | `payload_too_large` |
| 坏 gzip（头解析失败 / 解压失败 / XLEN 越界） | 400 | `bad_gzip` |
| 空包（multipart 文件字段 0 字节） | 400 | `empty_payload` |

前端只对 `payload_too_large` 做"历史太长"的中文提示（`web/index.html:786`），
其余显示 `error` 文案，前端不需要改。

## 二、预算检查改减式（防和式溢出）

`UPLOAD_FILE_WRITE` 原先把前缀与本次分块相加再跟预算比：明文的
`g_workLen + need > g_uploadCap`、gzip 的 `g_uploadBody.length() + need > g_uploadCap`。
值域上不会溢出（两者都 ≤ cap ≤ 48,128，分块 ≤ ~1,460），但写法上是先把两个大数交给
加法、再进比较。改为 `need > g_uploadCap - have`，`have` 始终 ≤ cap（每轮开始清零、
每块写入前都先判），等价且不再依赖"和不会绕回"这个前提。日志相应改成两段分开打印。

实测：明文 60 KB 超限时串口打印
`[web] reject upload: plain 47388+1436 bytes over cap 48128`，HTTP 回 413 `payload_too_large`。

## 三、gzip FEXTRA 直接校验 XLEN

原 `gzipParse()` 的 FEXTRA 分支只查 `off + 2 > gzLen`（2 字节 XLEN 本身不越界），
XLEN 指向文件外的坏包要等末尾 `off + 8 >= gzLen` 才发现，期间越界的 `off` 还继续参与
FNAME / FCOMMENT / FHCRC 的偏移运算。

改为读完 XLEN 立刻用减法判：`gzLen - off < 2`、`gzLen - off - 2 < xlen`，超界当场
`return false`。对合法 gzip（含带 FEXTRA 的）行为不变。
